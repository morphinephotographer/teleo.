# Data, recovery and iCloud

Portable JSON: `{ "version": 1, "scripts": [...] }`. Required script fields: UUID scriptId, title/body strings, ISO8601 createdAt/updatedAt, complete reading preferences; optional folderId. Unicode and line breaks are preserved, empty scripts are legal. Import limits: 10 MB file, 1000 scripts, 2 million text characters per JSON script. Preferences are range checked; future versions are rejected. Imports create new local IDs to avoid overwriting existing or tombstoned content. Folder records and revision history are not included in portable v1 exports; exports are content migration/backups, not a full database clone.

Browser IndexedDB v1 stores scripts, revisions and folders. Edits queue immediately, flush every 600ms and on blur/navigation/visibility/pagehide. A synchronous per-script localStorage recovery journal protects pending edits when available; failed saves retain pending edits and expose an export warning. Revisions snapshot previous text/title at save checkpoints and retain at most 30 versions / 5 MB per script. Script deletes retain tombstones indefinitely (no unsafe time-based purge). Folder deletion detaches scripts. Playback position stays in per-device localStorage and is never exported or sent to the relay.

Native SwiftData schema v1 has ScriptRecord, RevisionRecord, FolderRecord: default values for required properties, optional UUID folder references, no unique constraints, no relationships. VersionedSchema + SchemaMigrationPlan define the initial version; no destructive migration or store deletion fallback exists. If startup fails, the UI reports the error and preserves the store. Before editing, a revision checkpoint saves the starting content; debounced checkpoints save subsequent versions, bounded at 30 / 5 MB. Tombstones are retained indefinitely. Restore saves a checkpoint before applying an earlier snapshot. Last-writer behavior may overwrite the visible record under concurrent cloud edits; independently saved immutable revisions aid recovery, but conflict-free merging is NOT implemented or verified.

## Configure signed iCloud builds

1. Open `apps/apple/Teleo.xcodeproj`. Choose your real Apple developer Team and suitable unique app IDs for both targets. Default bundle IDs `cc.teleo.ios` and `cc.teleo.mac` are development placeholders, not registered identities.
2. Add iCloud capability, enable CloudKit on both apps, create/select the **same** container. Intended naming is `iCloud.cc.teleo` if the owner can register it; no container ownership is assumed.
3. Add `com.apple.developer.icloud-container-identifiers` array containing that identifier and `com.apple.developer.icloud-services = [CloudKit]` to each target's own entitlement file through Xcode. Add push notification entitlement through provisioning (do not invent an APS environment or Team ID).
4. Add Info.plist string **TeleoCloudContainer** with the exact same identifier in both targets. Without it, Store explicitly uses `.none` and local disk. Use the SAME local store when enabling cloud; back it up first. Do not switch stores on account changes.
5. Enable Background Modes → Remote notifications for iOS (`UIBackgroundModes` array: `remote-notification`) and the corresponding macOS remote notification capability/configuration. Register signed apps for remote notifications as part of signed integration; current local build does not claim push delivery.
6. Initialize the development schema following Apple's documented Core Data bridge when needed; inspect records in CloudKit Console, then promote the additive schema to production only after owner review. Do not delete/change production field types. Test upgrades against a backed-up old store before adding any new schema stage.
7. Run the physical matrix below on signed devices. Signing, schema deployment and account access have not been performed by this task.

UI distinguishes Saved on this device, iCloud available with sync pending/unknown, and iCloud unavailable. A local save NEVER marks a record cloud-synced. The account check runs at launch and on CKAccountChanged; persistent CloudKit error notifications surface a backup warning. Quota-specific diagnostics and reliable observed-remote-change UI remain release gaps. Signed builds register for remote notifications only when a CloudKit identifier is configured. Local work is never wiped on account errors. Export backups before account transitions. Simulator/local model tests do not prove real two-device sync.

Official constraints reviewed on 2026-10-26: [Apple SwiftData sync](https://developer.apple.com/documentation/swiftdata/syncing-model-data-across-a-persons-devices).
